# ADR-001: Selection of Core Technology Stack (FastAPI + PostgreSQL + React)
- Date: 2026-09-20
- Status: Accepted
- Context: We need a high-performance, auditable, and modular tech stack for Family360 to ingest welfare records, evaluate deterministic eligibility logic, perform entity resolution, and render intuitive citizen & administrative views for Gujarat Family ID.
- Decision: We adopt Python 3.10+ with FastAPI for the backend, PostgreSQL with SQLAlchemy 2.0 and Alembic for persistence, and React 18 with Vite and Tailwind CSS for the frontend.
- Alternatives considered:
  - **Django / Django REST Framework**: Rejected because Django's heavy monolithic ORM and convention-over-configuration add unwanted overhead for lightweight microservices, custom mathematical entity resolution pipelines (RapidFuzz, scikit-learn), and async streaming. FastAPI provides automatic OpenAPI generation, native Pydantic v2 validation, and async ASGI throughput with minimal boilerplate.
  - **Node.js / Express**: Rejected because while Node handles high-concurrency I/O well, Python is the indispensable ecosystem for dataset synthesis (pandas, numpy, faker), mathematical string-matching and fuzzy entity resolution (rapidfuzz, scikit-learn), and subsequent AI/LLM integration. Keeping backend and data science/ML in one language eliminates inter-process serialization overhead.
  - **Firebase / NoSQL (MongoDB)**: Rejected because social registry data is fundamentally relational: families have members, members link to multi-source identity records, schemes have structured criteria rules, and benefits link members to schemes. A relational schema with strict foreign keys, transactional ACID integrity, and indexing (PostgreSQL) prevents orphaned records and allows auditable joins.
- Consequences:
  - *Positive*: First-class type safety with Pydantic v2; automatic interactive Swagger documentation (/docs); direct access to Python's ML/data libraries; rock-solid relational consistency with PostgreSQL; rapid, component-driven UI development in React.
  - *Trade-offs*: Managing database schema migrations via Alembic requires discipline; async DB access must be carefully managed compared to simple BaaS setups.
