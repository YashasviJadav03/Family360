# ADR-003: Entity Resolution Architecture — Blocking & Weighted Explainable Scoring vs. Brute-Force vs. Black-Box ML
- Date: 2026-09-20
- Status: Accepted
- Context: A fundamental welfare delivery challenge in Gujarat Family ID is reconciling fragmented records across departmental silos (ration, health, scholarships, housing). Because citizens appear with minor spelling variations (e.g., "Rajesh Kumar Patel" vs. "R.K. Patel"), data entry errors, or typos, we must identify records representing the same individual.
- Decision: We implement candidate blocking (partitioning by `district` + `first-letter-of-name`) followed by an explainable, weighted deterministic scoring function using RapidFuzz.
- Mathematical Scoring Formula:
  $$\text{Match Score} = 0.35 \times \text{Name} + 0.25 \times \text{DOB} + 0.15 \times \text{Address} + 0.15 \times \text{Ration Card} + 0.10 \times \text{Gender}$$
  - $\ge 0.85$: "Likely Duplicate" (automatic high-confidence recommendation)
  - $0.65 \le \text{Score} < 0.85$: "Possible Duplicate — Needs Review" (surfaced to officer review queue)
  - $< 0.65$: "Not a Match"
- Alternatives Considered:
  - **Brute-Force Pairwise Comparison ($O(N^2)$)**:
    - With $N = 15,023$ identity records, brute-force requires $\frac{N(N-1)}{2} \approx 112.8 \text{ million}$ pairwise comparisons, taking minutes and causing database CPU saturation.
    - Blocking reduces comparisons by over **96%** (to $\approx 3.5 \text{ million}$ within matching blocks) while retaining true positive recall.
  - **Supervised Black-Box ML / Deep Learning Embeddings**:
    - Deep learning / black-box classifiers cannot produce human-auditable reasons required in administrative governance. When an officer merges citizen benefits, they must see *why* (e.g., "89% name similarity", "identical DOB", "same ration card"), not an unexplainable sigmoid output.
- Scale Considerations (Hackathon vs. Production DPI):
  - At hackathon scale (15,000 records), in-memory Python blocking runs in seconds.
  - At Gujarat scale (~1.5 crore citizens) or India scale (~140 crore records):
    1. Synchronous API comparison is impossible; matching must run as an asynchronous batch/streaming pipeline (e.g., Apache Spark / Flink or nightly Celery/Redis stream workers).
    2. Exact blocking alone fails on misspelled first names (e.g., "Ghanshyam" vs. "Ganshyam"). Production requires inverted fuzzy indexing in Elasticsearch/OpenSearch or Locality-Sensitive Hashing (LSH) / MinHash over phonetically encoded tokens (Soundex/Metaphone).
